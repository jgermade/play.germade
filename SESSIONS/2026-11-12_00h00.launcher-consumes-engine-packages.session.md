# Launcher consumes the independent engine packages

2026-11-12 · continues [2026-07-09_21h44.engine-subprojects-split](2026-07-09_21h44.engine-subprojects-split.session.md)
· cross-repo plan: [wasm-gaming.github.io SESSIONS/2026-11-12_00h00.homogenize-engine-integration](https://github.com/wasm-gaming/wasm-gaming.github.io/blob/claude/happy-hypatia-jot71i/SESSIONS/2026-11-12_00h00.homogenize-engine-integration.session.md)

**Status:** plan, pending approval. Nothing is implemented until approved.

## Goal

`play.germade` becomes a Netflix-style launcher that is a **pure consumer** of the wasm-gaming
engines: one generic player drives every engine through `@wasm-gaming/engine-specs`, and the
launcher holds no engine build scripts, no per-engine shells and no per-engine pages.

## Rules (confirmed by the owner, 2026-11-12)

1. **Every repository works on its own.** An engine repo clones, builds, tests and previews with
   no other wasm-gaming repo present; the launcher builds with no engine repo cloned.
2. **`@wasm-gaming/engine-specs` is the one exception**: it is a dependency of every engine
   (`dependencies`, caret range, never `*`) and of the launcher.
3. **Every engine has its own namespace in WASMFS** (see below).

## Where the launcher is today

The split started on 2026-07-09 but the launcher side never happened:
- `scripts/engines/{rsdkv3,rsdkv4,rsdkv5,fbneo,jgenesis,blastem,celeste,smw}/` still build engines here;
- each game/console has its own shell (`scripts/games/*/index.html`, `scripts/consoles/*/index.html`,
  `public/console/neo-geo/`), each wiring the engine its own way;
- `src/data/games.ts` points at those pages via `urlPath`;
- cross-cutting host code: `public/shared/game-input.js`, `public/shared/launcher-overlay.js`.

Meanwhile the engine repos moved on: rsdkv4 and ppsspp are on contract 0.3.2 (class API); the
other ten are on the legacy `{ manifest, load }` API (see the cross-repo plan).

## WASMFS namespace per engine

Today the namespace is chosen by the host and is **not** prefixed by the engine:
- rsdkv4 mounts the OPFS root at `/data`, so `storage({ namespace })` *is* the OPFS path and its
  default is `default/` — the same default snes9x, mGBA and geolith use (`storageNamespace ?? 'default'`).
  Two engines left on defaults share one folder.
- ppsspp uses `/home/web_user/.config/<namespace>` (default `ppsspp`); others are MEMFS/IDBFS with
  ad-hoc paths.

Rule, enforced by the engine, not by host convention:

```
OPFS root (= WASMFS /data)
└── <engine-id>/            ← owned by the engine, = static id of its SDK class
    └── <namespace>/        ← chosen by the host; default "default"
        ├── <assets>        (Data.rsdk, ROM, BIOS…)
        ├── <config files>  (settings.ini…)
        └── <saves>         (SData.bin, SRAM, states…)
```

- The engine prefixes its `static id`; a host can only pick the sub-folder. Segments are
  sanitized and `..` / absolute paths are rejected (rsdkv4's `normalizeStorageNamespace` already
  sanitizes; it just lacks the prefix).
- One helper in engine-specs (`storagePath(id, namespace)` + the sanitizer) so twelve engines
  do not each reimplement it — legitimate because engine-specs is the allowed dependency.
- The SDK exposes the resolved path (`play.storage()` → `{ namespace, path: 'rsdkv4/sonic-1' }`)
  so a host can pre-stage assets through the plain OPFS API without guessing.
- The launcher always passes the **game slug** as namespace: `rsdkv4/sonic-1`, `rsdkv4/sonic-2`,
  `rsdkv3/sonic-cd`, `fbneo/neo-geo`…
- Engines without OPFS mounting (MEMFS builds) use the same layout for the host-side mirror of
  their saves, so the tree is identical whatever the backend.
- Migration: rsdkv4 hosts that already pass `rsdkv4/Sonic1` keep working by passing `Sonic1`;
  a one-time move of a top-level `default/` into `rsdkv4/default/` on first boot.

## Model: engines vs games

- **Engine** = an npm package `@wasm-gaming/<id>-wasm`, contract 1.0 class, self-contained ESM
  (contract runtime bundled), wasm next to the SDK (`jsUrl` / `wasmUrl` overridable, as rsdkv4).
- **Game** = a catalog entry in `src/data/games.ts`:

```ts
interface GameEntry {
  slug: string;                 // also the storage namespace
  title: string; description: string; coverUrl?: string; bannerUrl?: string; youtubeId?: string;
  category: GameCategory; status: GameStatus;
  engine: string;               // static id: 'rsdkv4' | 'fbneo' | …
  config?: Record<string, unknown>;   // engine config patch
  options?: Record<string, unknown>;  // session options patch
  assets: Record<string, AssetSource>; // 'hosted' url | 'user' (picker / OPFS) | 'persisted'
}
```

Sonic 1 and Sonic 2 become two entries on one engine (`rsdkv4`), differing only in `assets.pack`
and `slug`.

## How the launcher consumes an engine

1. `npm i @wasm-gaming/<id>-wasm@^x.y` (pinned per engine; the wasm ships in the package).
2. A build step copies `node_modules/@wasm-gaming/<id>-wasm/dist/<id>/` to `public/engines/<id>/`
   (no Docker, no compile in this repo).
3. One generic player page `/play/?game=<slug>`, loaded in an **iframe** from the grid:
   - isolates Emscripten globals, SDL's `#canvas` lookup and keyboard listeners per engine;
   - returning to the grid = drop the iframe, which frees memory even for engines that cannot be
     restarted in process (rsdkv4 says so explicitly);
   - the player does `import('/engines/<id>/<id>.sdk.js')`, then
     `new Sdk({ config }).storage({ namespace: slug }).assets(…).mount(stage).start(options)`.
4. Generic host UI built from the contract, no engine knowledge:
   - settings panel painted from `sdk.config()` / `sdk.options()` descriptors (`live` → apply
     now vs restart);
   - asset step driven by the `assets` spec (`allowedTypes`, required/optional) → hosted fetch,
     file picker or already-persisted file in `<engine-id>/<slug>/`;
   - ESC overlay: resume / settings / restart / back to grid, using `pause()` / `resume()`;
   - `game-input.js` (gamepad → keyboard) and fullscreen stay here as host concerns, fed by the
     engine's declared input preset.
5. COOP/COEP for engines that need threads/OPFS mount (ppsspp, celeste): headers on the dev
   server and `coi-serviceworker` on static hosting.
6. Engine-specific extras (rsdkv4 start screens / dev menu) come later as an optional extension
   slot; the first version is generic only.

## Extension · 2026-11-12 — The current launcher is a first proof of concept

Owner's note: play.germade.dev, with the content it has today, is an **initial test**. What it
proves is the *experience*, not the integration:

- console/Netflix-style rows of covers, a hero with title, status and description;
- keyboard and gamepad navigation (↑↓ rows, ←→ cards, Enter);
- per-game **Install / Play**: assets staged once into OPFS, then Play directly.

Consequences for this plan:

1. **Rebuild, don't migrate.** The new launcher keeps that UX and starts clean: no
   `scripts/engines/`, `scripts/games/`, `scripts/consoles/`, `public/console/` carried over and
   deleted later. Phase 5 disappears; old pages are simply not ported.
2. **Done criterion relaxed:** a game is done when it plays through the generic player, not
   "as well as the prototype page did" — prototype-only hacks are re-evaluated, not copied.
3. **Install = staging into the engine's namespace.** "Install" writes the game's assets into
   `<engine-id>/<slug>/` (the engine-owned WASMFS/OPFS path, read from the SDK's `storagePath`),
   and the card shows Play when the engine's required assets are already there. This replaces the
   per-game `.ContentExists` markers of the prototype.
4. Catalog rows come from data (`games.ts` with `engine`), so a new engine is a package install
   plus entries, never a new page.

## Extension · 2026-11-12 — UI built with jq79

Owner's decision: the launcher UI is built with **[jq79](https://github.com/jgermade/jq79)**
(single-file components, Svelte-style `:setup` scripts, proxy reactivity, no compiler), the same
runtime as rsdkv4-wasm's `craft` host. **Astro is dropped.**

- **Stack:** `jq79` pinned in `package.json` + Vite with the bundled `jq79/vite` plugin (`.html`
  components import as modules, HMR in dev, static `dist/` for Pages). No CDN "latest" URL:
  craft's `import … from 'https://jgermade.github.io/jq79/jq79.js'` is exactly what this plan avoids.
- **Reference to copy, not to import:** craft's layout — `App.html`, `views/`, `components/`,
  `layout/`, `services/*.service.js` holding state, `C79.fetch('./App.html').mount('body > main')`.
- **Components (first cut):**
  - `App.html` — routes between the browse view and the player overlay;
  - `views/Browse.html` — hero (`Hero.html`) + rows (`Row.html` → `Card.html`), keyboard/gamepad focus grid;
  - `views/Player.html` — the iframe hosting `/play/?game=<slug>`, ESC overlay (`EscMenu.html`);
  - `components/Settings.html` — painted from the engine's `config()` / `options()` descriptors;
  - `components/Install.html` — driven by the engine's `assets` spec (picker / hosted fetch).
- **Services:** `catalog.service.js` (games.ts data + engine ids), `install.service.js` (OPFS
  staging under the SDK's `storagePath`, installed/not-installed state), `input.service.js`
  (keyboard + Gamepad API focus navigation, reused by the ESC overlay), `engine.service.js`
  (dynamic `import()` of `/engines/<id>/<id>.sdk.js`, used by the `/play/` page).
- The `/play/` page is a separate tiny jq79 entry, so the iframe loads only the player, not the
  browse UI.
