# Sonic Mania Integration

## Topic: Add Sonic Mania, following the same pattern as Sonic 1/2/3

- **Status:** Done

### Research

`src/data/games.ts` already has a `sonic-mania` entry (status `wip`).

**Upstream decompilation:** `RSDKModding/Sonic-Mania-Decompilation` (successor to the original Rubberduckycooly repo, now maintained under the RSDKModding org), built on top of `RSDKModding/RSDKv5-Decompilation` ("RSDKv5U" — RSDKv5 with community updates). Both use **CMake**, not the RSDKv4 decompilation's simple `Makefile`. Requires the user to legally own Sonic Mania (Steam/Epic/console) and extract its own data files — same shape of requirement as Sonic 1/2/3's ROM/`Data.rsdk`.

**Key difference from Sonic 1/2/3 (the actual risk here):** unlike RSDKv4 (Sonic 1/2), which already had a community Emscripten fork with a ready `wasm:` Makefile target we could adapt (`mattConn/Sonic-Decompilation-WASM`), and unlike Sonic 3 A.I.R., which publishes its own **official** prebuilt web release — **there is no equivalent for Sonic Mania**:
- The official `RSDKv5-Decompilation`'s `platforms/` folder only has `Android.cmake`, `Linux.cmake`, `NintendoSwitch.cmake`, `Windows.cmake` — **no Emscripten/web platform file exists upstream**.
- The official build guide (rsdkmodding.com) documents Windows/Linux/Switch/Android only; no mention of Emscripten/WASM anywhere.
- The only web ports found (`VinMannie/SonicManiaWeb`, forked as `burnedpopcorn/SonicManiaPlusWebPort` and `ReneGamer2368/SonicManiaPlusWebPort`) are, on inspection, **the same kind of unreproducible artifact we explicitly rejected during the Sonic 3 session**: just a dumped `RSDKv5.html`/`.js`/`.wasm` output with no CMake/build scripts/source included, unclear provenance, and — per the original author's own repo description — **"MAIN MENU CRASHES!!!! Press (Esc) to use Dev Menu to access levels."**, i.e. known-broken. Not something we can rebuild, patch, or trust the licensing/integrity of.

So, unlike our last three integrations (adapt an existing WASM build, or fetch an official web release), **getting Sonic Mania running in the browser would require building an Emscripten target for RSDKv5 essentially from scratch ourselves** — writing a new CMake Emscripten toolchain integration (an `Emscripten.cmake` platform file or `emcmake`-driven build), wiring up SDL2/audio/rendering dependencies for a considerably larger codebase (RSDKv5 decompiles "virtually any platform that can run RSDKv5", per its own README, but web isn't one of the platforms anyone has proven out with a maintainable source build) with "600+ game objects" (much bigger than RSDKv4's Sonic 1/2 scope). This is open-ended reverse-engineering-adjacent build engineering, not a known-good recipe we're adapting — real risk of getting stuck deep in engine/dependency issues with no reference implementation to fall back on.

### Options

1. **Build our own Emscripten/CMake port from source** (clone `Sonic-Mania-Decompilation` + `RSDKv5-Decompilation` submodule, write a new CMake Emscripten platform file, get SDL2/audio linking correctly, likely a multi-session effort with real risk of dead ends) — matches our established "build it ourselves, don't vendor untraceable binaries" principle, but is a substantially bigger and riskier undertaking than any prior integration.
2. **Vendor one of the existing prebuilt web dumps anyway** (`VinMannie/SonicManiaWeb` or a fork) — fast, but goes directly against the precedent we set explicitly in the Sonic 3 session (unclear provenance/licensing, can't rebuild/patch), and the original author's own description says the main menu crashes.
3. **Defer** — leave `sonic-mania` as `status: "wip"` for now and revisit as a dedicated, larger effort later (possibly after Quake/Doom or other lower-risk items).

### Decision

User chose **Option 1: build the Emscripten port ourselves**, matching our established principle of building from source rather than vendoring unclear-provenance binaries.

### Further Research: is this actually feasible? (cloned both repos to check)

Cloned `RSDKModding/Sonic-Mania-Decompilation` (recursively, pulling in its `dependencies/RSDKv5` submodule → `RSDKModding/RSDKv5-Decompilation`, itself pulling `stb_vorbis` and `tinyxml2` as sub-submodules) into `.tmp/research-mania/` to inspect the actual CMake structure before committing to a plan. Findings meaningfully **de-risk** this compared to the initial "black box" framing above:

1. **Dependency footprint is small and portable.** Audio decoding uses `stb_vorbis` (single-header, vendored as source — no system `libvorbis` needed at all, simpler than RSDKv4's approach). XML parsing (`tinyxml2`), INI parsing (`iniparser`), and zip handling (`miniz`) are all vendored, portable C/C++ compiled directly into `RetroEngine` — no exotic dependencies.
2. **A `RETRO_SUBSYSTEM=SDL2` renderer backend already exists** (`RSDKv5/RSDK/Graphics/SDL2/SDL2RenderDevice.cpp`, ~1100 lines) that uses plain `SDL_CreateRenderer` (SDL2's 2D renderer API) — **not** raw OpenGL/GLSL shaders like the default `OGL` subsystem (which needs GLFW+GLEW, a much worse fit for Emscripten). This is the same class of renderer RSDKv4 already uses successfully in our Sonic 1/2 Emscripten build, so we already know this rendering approach works under Emscripten's SDL2 port.
3. **Platform selection is a single `include(platforms/${PLATFORM}.cmake)`** in RSDKv5's `CMakeLists.txt` — Windows/Linux/Android/NintendoSwitch each have their own file there; **we'd write a new `platforms/Emscripten.cmake`**, modeled closely on the existing `Linux.cmake` (same `RETRO_SUBSYSTEM=SDL2` branch), but swapping its `pkg-config`-based dependency lookups for Emscripten's built-in port flags (`-s USE_SDL=2`), and compiling `libogg`/`libtheora` from source via CMake `add_library` (Linux.cmake already has a "compile from source if pkg-config doesn't find it" fallback path we can lean on/adapt) — same shape of solution as RSDKv4's `-s USE_OGG=1 -s USE_VORBIS=1` flags, not novel.
4. **Must force `GAME_STATIC=ON`.** By default (top-level `CMakeLists.txt`), `GAME_STATIC` is only forced `ON` for non-Windows/non-Unix platforms; Emscripten's toolchain sets `UNIX=1`, so left alone it would default `OFF` — meaning the "Game" logic would build as a separate shared library, dynamically loaded by `RetroEngine` at runtime. That's real, unnecessary complexity under Emscripten (side-modules/`dlopen`). We'll explicitly pass `-DGAME_STATIC=ON` so everything links into one single `.wasm`, avoiding Emscripten dynamic-linking entirely.
5. **Audio backend:** default is MiniAudio; `Linux.cmake` shows a `USE_SDL_AUDIO` flag to use SDL2's audio API instead. Recommend enabling that for parity with our proven RSDKv4 SDL2-audio Emscripten experience (which already needed a specific `SDL_InitSubSystem(SDL_INIT_AUDIO)` ordering patch — may need something similar here, to be confirmed once we're actually compiling).
6. **Assets:** same shape of requirement as Sonic 1/2/3 — user must own the game and provide its data files (RSDKv5 reads from a `Data/` path, e.g. `Data/Game/GameConfig.bin`, `Data/Game/Game.xml`). Exact format (a single packed archive vs. a raw extracted folder tree) needs confirming once we're implementing — not blocking for planning purposes, same as how Sonic 3's ROM-extraction specifics were deferred to implementation time.

**Net assessment:** still more original engineering than Sonic 1/2/3 (nobody has proven out an Emscripten build of this specific codebase before), but the pieces are simpler and more portable than initially feared — no shader/GL rewrite needed, no exotic audio/video codec integration, no dynamic linking if we force static. This is closer in spirit to "adapt Linux.cmake to Emscripten" than "solve unknown deep engine problems."

### Implementation

User approved ("adelante con el plan") and dropped `game-assets/sonic-mania/Data.rsdk` in place. Built the Emscripten port for real, iterating against the actual compiler/browser rather than guessing further:

1. **`dependencies/RSDKv5/RSDK/Core/RetroEngine.hpp`** patched (via the build script, against a fresh clone each time) to add a `RETRO_EMSCRIPTEN` platform: detection (`#elif defined __EMSCRIPTEN__`, since emcc defines `__EMSCRIPTEN__`/`__unix__` but *not* `__linux__` — confirmed via `emcc -dM -E`, so without this it silently fell through to the `RETRO_WIN` branch and tried to `#include <windows.h>`), and a platform-init branch forcing `RETRO_RENDERDEVICE_SDL2`/`RETRO_AUDIODEVICE_SDL2`/`RETRO_INPUTDEVICE_SDL2`, mirroring the OSX/iOS branch.
2. **`RetroEngine.cpp`** patched: `RunRetroEngine()`'s main loop is a native-style blocking `while` that busy-waits on `CheckFPSCap()` — fine natively, but it would hot-spin the browser's single thread and never yield. Fix: `-sASYNCIFY=1` plus one `emscripten_sleep(1)` call when the FPS cap hasn't been hit yet, requiring no restructuring of the rest of the function.
3. **New `dependencies/RSDKv5/platforms/Emscripten.cmake`**, modeled on `Linux.cmake`'s `SDL2` branch. Two real, non-obvious findings from actually compiling:
   - Neither libogg nor libtheora (used by `Video.cpp` for cutscenes) have system packages under Emscripten, and unlike Android's `COMPILE_OGG`/`COMPILE_THEORA` fallback, this decompilation repo **doesn't actually vendor either library's source** (only a stray `config_types.h` is tracked) — so the build script clones `xiph/ogg` and `xiph/theora` (pinned commits) and drops their `src`/`lib` files into the exact paths RSDKv5's shared `CMakeLists.txt` expects. One upstream file (`cpu.c`) referenced in that hardcoded file list doesn't exist in real xiph/theora (nothing calls the symbol it would have defined) — satisfied with an empty stub.
   - `ALLOW_MEMORY_GROWTH=1` makes Chromium back the wasm heap with a "resizable" `ArrayBuffer`, which its `TextDecoder.decode()` *and* WebGL upload calls (`texSubImage2D`, hit via `glShaderSource`'s string conversion and sprite texture uploads) both outright refuse ("must not be resizable"). Fixed by using a fixed-size heap (`-sTOTAL_MEMORY=512MB`, no growth) instead of chasing per-call-site workarounds.
4. **`scripts/sonic-mania/build-sonic-mania-docker.sh`**: clones `Sonic-Mania-Decompilation` + `ogg` + `theora` at pinned commits, applies the two source patches via python (assert-counted, same style as the Sonic 1/2 script), writes `Emscripten.cmake` and a minimal `Settings.ini`, builds via `emcmake`/`cmake --build` in the `emscripten/emsdk:latest` Docker image, copies `RSDKv5U.{js,wasm,data}` to `public/game/sonic-mania/`. Verified end-to-end against a **fresh clone** (not just the hand-patched research copy).
5. **`scripts/sonic-mania/index.html`**: same shape as Sonic 3's shell (AudioContext resume, `window.__launcherReturnViaEscMenu = true` + `/shared/launcher-overlay.js`), since RSDKv5 has no native dev-menu web bridge yet (no `WebDevMenu.cpp` equivalent built this round).
6. `Makefile` (`build.sonic-mania`), `.gitignore` (`public/game/sonic-mania/*`), `src/data/games.ts` (`status: "wip"` → `"ready"`) updated.

Verified: real Sonic Mania Plus splash screen and boot animation render correctly (screenshotted via headless Chromium against both a standalone static server and the actual Astro dev server at `/game/sonic-mania/index.html`), audio initializes without error, no console errors during boot. Not yet verified: cutscene (Theora) playback, gamepad input (RSDKv5's SDL2 input backend has no RSDKv4-style forced controller-mapping fallback — untested with a real gamepad), and memory headroom under the fixed 512MB heap for larger levels.

### Follow-up: runtime crash during actual gameplay

User played it for real and hit `Uncaught (in promise) RuntimeError: function signature mismatch` deep in the wasm call stack (via `doRewind`) shortly after entering menus/gameplay — something the intro-screen-only verification above hadn't exercised.

Root-caused by reproducing it locally (headless Chromium driven through the menus into gameplay) and testing hypotheses against the real build rather than guessing:

1. **First hypothesis (wrong, but disproved cleanly): Asyncify.** The original fix for the main-loop-freezing problem used `-sASYNCIFY=1` + one `emscripten_sleep(1)` call (see above). Asyncify has known bugs around indirect calls through function-pointer tables, which is exactly RSDK's object/mod dispatch style, so this was the natural suspect. Rebuilt with Asyncify **removed entirely** — restructured `RunRetroEngine()`'s loop body into a separate `RunRetroEngineFrame()` called via `emscripten_set_main_loop()` instead (every old `continue` → `return`, the loop's `break` → `emscripten_cancel_main_loop()` + shutdown). This is strictly better regardless (no sleep/yield primitive needed at all, ~45% smaller `.wasm`) — but the crash **still reproduced** with Asyncify completely gone, disproving the hypothesis. Good thing it was actually re-tested rather than assumed fixed.
2. **Real cause: RSDK/Mania's object system calls Update/Draw/etc. through generic function-pointer tables, and some registered functions don't exactly match the pointer type they're called through** — undefined behavior that native ABIs silently tolerate but wasm's `call_indirect` does not, trapping instead. Only reproduces once you actually enter a zone and play, which is why the intro-only smoke test missed it.
3. **Fix:** `-sEMULATE_FUNCTION_POINTER_CASTS=1`, an Emscripten flag built for exactly this (routes mismatched indirect calls through a runtime-adapting wrapper instead of trapping). Hit a secondary wall immediately: `wasm-opt`'s `--fpcast-emu` pass refused to run ("max-func-params needs to be at least 17") against its own default limit; fixed with `-sBINARYEN_EXTRA_PASSES=pass-arg=max-func-params@17` (raw pass-arg injection, since Emscripten has no dedicated setting for this).
4. Re-verified with the same repro steps (headless Chromium mashing through menus into a character-select screen and beyond) against a build produced by the **updated production build script from a fresh clone** — no crash.

`scripts/sonic-mania/build-sonic-mania-docker.sh` and `dependencies/RSDKv5/platforms/Emscripten.cmake`'s generation updated accordingly (Asyncify flags removed, `RunRetroEngineFrame`/`ShutdownRetroEngine` restructuring patch replaces the old `emscripten_sleep` patch, `EMULATE_FUNCTION_POINTER_CASTS` + `BINARYEN_EXTRA_PASSES` added).
