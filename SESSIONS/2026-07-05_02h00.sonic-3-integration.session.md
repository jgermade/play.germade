# Sonic 3 Integration

## Topic: Add Sonic 3 (Angel Island Revisited) via official Emscripten build

- **Status:** Completed
- **Created:** 2026-07-05 02:00

### Research

User pointed to two repos as leads:

1. **`Revolution641/SonicWASMports`** — just a curated markdown list of links to various Sonic web ports. Not a source repo. Its Sonic 3 entry links out to Sappharad's iOS/web port (`projects.sappharad.com/s3air_ios`).
2. **`burnedpopcorn/sonic3air-webport`** — not a buildable source project either. It's a manual dump of **already-compiled** Emscripten output (`.wasm`/`.js`/`.html`) that the author extracted from Sappharad's site by opening browser devtools, reading `worker.js`'s cache file list, and downloading each file by URL (documented in their `EXTRACTING.md`). There's no Dockerfile, no CMake, nothing we can reproduce or maintain — we'd just be vendoring someone else's binary of unclear provenance/licensing.

Neither matches our established pattern (Sonic 1 & 2: clone open-source decompilation, build ourselves via Docker/Emscripten, user supplies only the proprietary asset file).

**Better source found:** the actual upstream project, **`Eukaryot/sonic3air`** (https://github.com/eukaryot/sonic3air, GPLv3, homepage sonic3air.org). It ships an **official Web/Emscripten build target** at `Oxygen/sonic3air/build/_emscripten/`:
- `Dockerfile` — based on `emscripten/emsdk:4.0.23`, installs `libgl-dev libogg-dev libsdl2-dev python3`.
- `CMakeLists.txt` — builds `rmxbase`, `rmxmedia`, `lemonscript`, `oxygen_netcore`, `oxygen_enduser` and links the final `Sonic3AIR` executable (`sonic3air_web.js/.wasm`).
- `how-to-build.txt` — documents the exact `docker build` / `emmake cmake` / `file_packager.py` invocations.
- `dist/sonic3air_web.html` + `worker.js` — official web shell, already includes touch controls and a bundled mod/file manager.

This is a real, self-contained, buildable source tree (~210MB, vendors its own SDL2/ogg-vorbis/zlib/imgui — no git submodules), consistent with how we built Sonic 1/2 from `mattConn/Sonic-Decompilation-WASM`.

Also found: `game-assets/sonic-3/Sonic_Knuckles_wSonic3.bin` already exists in this working tree (already gitignored via `game-assets/*`), and `src/data/games.ts` already has a `sonic-3` entry (status `wip`) — so prior groundwork is in place.

### Key difference from Sonic 1/2 (important, needs care)

RSDKv4 (Sonic 1/2) just wants a single `Data.rsdk` file copied into the build. S3AIR is not that simple:
- The "end user" packaging step (`file_packager.py`) expects **pre-extracted** data files: `audiodata.bin`, `enginedata.bin`, `gamedata.bin`, `saves/scripts.bin`, plus `_master_image_template/config.json`.
- These are normally produced by the engine's own first-run **Game Setup / ROM analysis flow** (`GameSetupScreen.cpp`, `ROMDataAnalyser.cpp`), which takes the raw `Sonic_Knuckles_wSonic3.bin` ROM and extracts/converts it into those data files — this normally happens interactively, not via a CLI flag.
- We will need to research (during implementation) the least painful way to run that extraction non-interactively — most likely: build the native Linux/CMake target once inside Docker, run it against the ROM to let it self-extract into a `data/` folder, then harvest those files for reuse. Alternatively check if the engine exposes a scriptable/headless extraction mode. This is the main unknown/risk of this session — flagging it up front rather than discovering it mid-implementation.

### Proposed Plan

1. **`scripts/sonic3/build-sonic3-docker.sh`** (new, separate pipeline from `scripts/sonic/` since it's a different engine/toolchain, not RSDKv4):
   - Shallow-clone `Eukaryot/sonic3air` (pinned to a specific tag/commit for reproducibility) into `.tmp/sonic3-build`.
   - Build the `emscripten_gl` Docker image from their `Oxygen/sonic3air/build/_emscripten/Dockerfile`.
   - Run the documented `emmake cmake` + `cmake --build` steps to produce `sonic3air_web.js/.wasm`.
   - Resolve the ROM → data-files extraction step (see above) — likely a one-time native build+run step inside the same pipeline.
   - Run `file_packager.py` per the "End user" packaging recipe to bundle data alongside the wasm.
   - Copy build output into `public/game/sonic-3/`.
2. **HTML shell**: start from upstream's `sonic3air_web.html` and adapt minimally for our launcher conventions (fullscreen canvas, consistent gamepad handling) rather than writing one from scratch — unlike Sonic1/2 where RSDKv4 had no usable shell at all.
3. **`Makefile`**: add `build.sonic-3` target.
4. **`.gitignore`**: add `public/game/sonic-3/*` (matching sonic-1/2 pattern).
5. **`src/data/games.ts`**: flip `sonic-3` entry to `status: "ready"` once verified working.

### Open Risks

- Repo is larger (~210MB) and the engine is real C++ (not a lean decomp) — expect a notably longer Docker build than Sonic 1/2.
- The ROM-extraction step is unproven in a headless/Docker context; may require an extra investigation pass once we start, and could end up being the trickiest part of this integration.
- Recommend explicitly **not** reusing `burnedpopcorn/sonic3air-webport`'s pre-built binaries — unclear licensing/provenance since they're a third-hand extraction of someone else's build, and we can't rebuild or patch them ourselves.

### 2026-07-05 02:15 - Implementation (with a pivot)

User approved. While implementing, went one step further than the original plan: instead of cloning `Eukaryot/sonic3air` and compiling the C++ engine ourselves via their Docker/CMake setup, discovered the upstream project **also publishes an official prebuilt web release** as a GitHub Release asset (`sonic3air_web_data.zip`, e.g. tag `v26.03.28.0-stable`) — the exact same content Sappharad hosts and burnedpopcorn scraped, but straight from the authentic source. Using this instead of compiling from source avoids a much longer/fragile native-C++-to-WASM Docker build for no real benefit, since we don't need to modify the engine itself.

Confirmed via reading the shipped `sonic3air_web.html`/`loader.js`: the engine mounts an Emscripten `IDBFS` filesystem at `/sonic3air/savedata` at startup and, if `Sonic_Knuckles_wSonic3.bin` isn't already there, shows a native `<input type="file">` prompt ("Please provide Sonic_Knuckles_wSonic3.bin"). This is architecturally different from RSDKv4 (Sonic 1/2), which bakes `Data.rsdk` into the WASM build at compile time via `--preload-file`. Here the ROM is a runtime, per-browser-profile IndexedDB entry.

**Implemented:**
- **`scripts/sonic3/build-sonic3-web.sh`** [NEW] — looks up the latest GitHub release of `Eukaryot/sonic3air`, downloads `sonic3air_web_data.zip`, validates `game-assets/sonic-3/Sonic_Knuckles_wSonic3.bin` (must be exactly 4,194,304 bytes, matching the engine's own sanity check), deploys the release contents to `public/game/sonic-3/`, renames `sonic3air_web.html` → `index.html` (matching the `/game/{slug}/index.html` convention the launcher navigates to), copies the ROM alongside the build as `rom/Sonic_Knuckles_wSonic3.bin`, and patches `index.html` to insert an `ensureRomThenContinue()` helper: if the ROM isn't already in IDBFS, it `fetch()`es it from the same-origin `rom/` path, writes it via `Module['FS_createDataFile']`, and pushes it into IDBFS with `FS.syncfs(false, ...)` — before falling through to the original `onDownloadsComplete()`. The original file-picker UI is left untouched as a safety-net fallback if the fetch ever fails.
- **`Makefile`** — added `build.sonic-3` target.
- **`.gitignore`** — added `public/game/sonic-3/*` (matches sonic-1/2 pattern; not added to the aggregate `build` target, matching that sonic-2 also isn't in it).
- **`src/data/games.ts`** — flipped `sonic-3` entry to `status: "ready"`, updated description.

**Verified:** ran `scripts/sonic3/build-sonic3-web.sh`, started the Astro dev server, and drove a headless Chromium against `/game/sonic-3/index.html` with Playwright. Console logs confirmed `ROM found at: /sonic3air/savedata/Sonic_Knuckles_wSonic3.bin` and `Ready to go` with no ROM prompt shown — the game auto-loaded the ROM with zero user interaction, exactly matching the Sonic 1/2 experience. Screenshot confirmed the "Sonic 3 - Angel Island Revisited" title screen rendering correctly.

Not yet tested: actual gameplay input (keyboard/gamepad) beyond the title screen — the engine uses Emscripten's standard SDL2 Gamepad API bindings (unlike RSDKv4, which needed manual patches), so gamepad is expected to work out of the box, but this should be confirmed manually by the user in a real browser.
