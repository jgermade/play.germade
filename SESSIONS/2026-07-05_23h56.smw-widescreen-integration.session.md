# Super Mario World widescreen integration (snesrev/smw + wide-snes)

- **Date:** 2026-07-05 23h56
- **Status:** In Progress

## Goal

Add **Super Mario World** to the launcher, compiled to WASM from the
`snesrev/smw` C reimplementation, with **widescreen** rendering in the spirit
of `VitorVilela7/wide-snes`. ROM provided by the user at
`game-assets/smario-world/smario-world-USA.sfc`.

> Proposal originally drafted inside
> `2026-07-05_21h00.sonic-cd-integration.session.md` (2026-07-05 23:50) and
> moved here after that session was capitulated.

## Research findings (2026-07-05)

- **ROM verified**: SHA1 `6b47bb75d16514b6a476aa0c73a683a2a4c18765` — exactly
  the USA ROM `snesrev/smw` expects. ✔
- **snesrev/smw** is a full C reimplementation (like `zelda3`): plain C +
  SDL2, no emulator required at runtime. Assets are extracted **at build
  time** from the ROM via `assets/restool.py` → `smw_assets.dat`; the ROM is
  not needed (and will not be shipped) afterwards.
- **Per-frame verification**: upstream normally runs an emulated SNES in
  parallel and diffs RAM every frame (2× CPU). When no ROM is present at
  runtime it automatically falls back to `RM_MINE` (pure C, no emulator) —
  ideal for the web build: we simply don't preload the ROM.
- **Widescreen is NOT implemented upstream** (issue snesrev/smw#52 open, no
  branch/PR). The scaffolding exists — `g_config.extended_aspect_ratio`,
  `g_snes_width = extended*2+256` in `main.c`, and the LakeSnes PPU (shared
  with zelda3) already renders `extraLeftRight` side columns — but it is dead
  code: no ini key parses it and `ppu->extraLeftRight` is never assigned.
- **wide-snes** is a BPS/ASM patch set (~30 files: `level_sprites.asm`,
  `level_render.asm`, `overworld.asm`, bosses, extended/cluster/score/bounce
  sprites, windowing effects, …) targeting the original ROM on a modified
  emulator. It cannot be applied directly to the C port, but it is a precise
  **reference map**: `snesrev/smw` functions carry their original ROM
  addresses in comments (e.g. `// 01f314`), so each wide-snes hook can be
  located and reproduced in C.

## Decisions (2026-07-05 23:56, user)

1. **Phasing**: Phase 1 ships in 4:3 first; Phase 2 adds 16:9 on top.
2. **Aspect ratio**: 16:9, but made **flexible** (see design note below).
3. **Slug**: `smario-world` (matches `game-assets/smario-world/`).

### Design note — flexible aspect ratio

Flexibility is cheap because everything downstream is already parametric:

- `ExtendedAspectRatio = W:H` ini key parses **any** ratio (like zelda3) and
  computes the extra side pixels from it: `extra = (192 * W/H - 256) / 2`
  (SNES pixels are displayed 7:6 wide; 256×224 ≡ 4:3), rounded to a sprite
  tile multiple. 16:9 → ~336–352 px internal width; 4:3 → 0 (vanilla).
- The HTML shell exposes `?aspect=W:H`: a `Module.preRun` hook rewrites the
  `ExtendedAspectRatio` line of `smw.ini` in MEMFS before `main()` runs, so
  one build serves every ratio. Default (no param): 16:9 once Phase 2 lands.
- All Phase 2 game-logic patches must be written against
  `g_config.extended_aspect_ratio` (never a hard-coded 352), so any ratio
  works. Practical ceiling ~21:9: beyond that, sprite spawn windows and the
  512px-wide VRAM tilemaps run out of off-screen headroom.

## Plan

### Phase 1 — Base integration (4:3), same pipeline as the other games

1. **Build** — `scripts/smario-world/build-smw-docker.sh`, modeled on the
   Celeste/Sonic scripts:
   - Fresh clone of `snesrev/smw`, patches applied at build time.
   - Asset extraction inside the container: `restool.py -e` against the
     user's ROM (copied as `smw.sfc` during build only).
   - Emscripten build porting the known-good patterns from previous games:
     `emscripten_set_main_loop` replacing the `while` loop (with lazy init),
     explicit `SDL_InitSubSystem(SDL_INIT_AUDIO)`, SDL2 renderer path (no
     OpenGL — `OutputMethod = SDL`, same lesson as Sonic CD), fixed memory
     (no `ALLOW_MEMORY_GROWTH`), `--preload-file smw_assets.dat
     --preload-file smw.ini`, output `index.js` for the custom HTML shell.
   - IDBFS (or localStorage bridge) for `saves/` so snapshots/SRAM persist.
2. **Config** — `scripts/smario-world/smw.ini`: `NewRenderer = 1`,
   `NoSpriteLimits = 1`, `DisableFrameDelay = 1` (rAF paces the loop),
   `Autosave = 1`, keyboard defaults kept.
3. **HTML shell** — `scripts/smario-world/index.html` from the Sonic one:
   `/shared/game-input.js` with an SNES keymap (upstream defaults: arrows +
   Enter/RShift + Z/X/A/S/C/V), `/shared/launcher-overlay.js` in
   Escape-mini-menu mode (`__launcherReturnViaEscMenu = true`, like Sonic 3 —
   smw has no dev menu of its own).
4. **Wiring** — `Makefile` target `build.smw`; `src/data/games.ts` entry
   (slug `smario-world`, cover art TBD); output to
   `public/game/smario-world/`.

### Phase 2 — Widescreen (the actual wide-snes part)

1. **Wire the dormant plumbing** (small, upstream-shaped): parse
   `ExtendedAspectRatio` in `config.c`, assign `ppu->extraLeftRight` at PPU
   init/reset, size the canvas from `g_snes_width`. Per the flexibility
   design note, everything derives from the parsed ratio.
2. **Expected immediate result**: BG layers mostly correct in horizontal
   levels (the tilemap already holds off-screen columns), but sprites
   spawn/despawn and many effects still assume a 256px window → pop-in at
   the old edges, HUD/layer-3 and windowing quirks.
3. **Port wide-snes game-logic patches to C incrementally**, using its ASM
   files as the checklist and the ROM-address comments in `smw_*.c` to find
   each site. Priority order: `level_sprites` (spawn/despawn margins) →
   `level_render` → extended/cluster/bounce/score/minor sprites →
   `windowing_effects` → `level_side_exits`/entrances → shooters/generators
   → bosses/`iggy_hair` → `goal_fix`/`feather_fix`/`smoke_position` misc.
4. **Screens that stay 4:3** initially (pillarboxed), as wide-snes itself
   does: title screen, overworld, credits. Revisit later if wanted.
5. 4:3 always remains available via `?aspect=4:3` (or ini) as fallback.

step 1 is small, but full fidelity across all of step 3 is a multi-session

steps 1–2 (playable widescreen with known sprite pop-in), then burn down the
patch checklist across future sessions.

## 2026-07-06 00:40 - Sub-60Hz rAF catch-up loop (user-approved)

User asked whether variable requestAnimationFrame rates were handled. They
were for >60Hz (accumulator skips surplus ticks; verified at 122fps rAF in
headless Chromium) but **not** for <60Hz: the accumulator ran at most one
logic frame per rAF tick, so a 30Hz display (or a throttled tab) played in
slow motion instead of catching up.

Change in `patch-smw-emscripten.py`: the accumulator moves out of
`RunOneFrameIteration()` into a new `EmscriptenFrameLoop()` wrapper (the
function registered with `emscripten_set_main_loop`), which now runs the
iteration in a catch-up loop — up to 4 logic frames per rAF tick, backlog
capped at ~4 frames (dropped when the tab was hidden). The 16.0ms (not
16.667) threshold is kept so vsync jitter at exactly 60Hz doesn't skip
frames. At <60Hz this renders more than once per tick (minor waste, correct
speed); the native build path is untouched.

Verified by re-running the Playwright script twice: normal (rAF ~120fps
headless) and with rAF forced to 30fps via `addInitScript` — the
time-driven overworld intro completes on the same wall-clock schedule in
both runs, confirming 60fps logic at 120, 60 and 30Hz tick rates.
