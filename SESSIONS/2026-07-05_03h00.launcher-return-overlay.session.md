# Launcher Return Overlay

## Topic: Add an in-game overlay/shortcut to return to the launcher

- **Status:** In Progress
- **Created:** 2026-07-05 03:00

### Problem

The launcher's "Play" action does a full-page navigation to `/game/{slug}/index.html` (see `src/pages/index.astro:513-514`) — it's not an iframe, it's a real page swap into each game's own static build. Once inside a game, there is currently no way back to the launcher except the browser's Back button (or manually editing the URL). We want an always-available, low-friction way to return to `/` from inside any game.

### Research: why this isn't a single central fix

Each game ships its own independent HTML shell, patched differently at build time — there's no shared layout/iframe to hook into centrally:

- **Sonic 1 & 2** share a custom shell we author and own directly: `scripts/sonic/index.html`. Copied as-is into `public/game/sonic-{1,2}/index.html` by `scripts/sonic/build-sonic-docker.sh`.
- **Sonic 3** deploys upstream's (`Eukaryot/sonic3air`) own prebuilt `sonic3air_web.html`, renamed to `index.html`. `scripts/sonic3/build-sonic3-web.sh` already does a post-deploy Python string-patch (inserting `ensureRomThenContinue()`), so there's precedent for patching this file after the fact.
- **Celeste** deploys upstream's (`MercuryWorkshop/celeste-wasm`) own `frontend/dist/index.html`. `scripts/celeste/build-celeste.sh` already runs a post-build Node patch script, `scripts/celeste/patch-gamepad-proxy.mjs`, which does the same kind of string-injection into `index.html`.

So the established pattern in this repo for "add behavior to a game's shell" is: **a small, targeted string-patch step run after each build**, not a shared template. The overlay should follow that same pattern rather than inventing a new one.

### Proposed Design

**1. One shared, static overlay script — single source of truth**

- New file: `public/shared/launcher-overlay.js`. Plain, dependency-free JS (no build step needed — it's a static asset Astro serves as-is at `/shared/launcher-overlay.js`, reachable from *any* `public/game/{slug}/` page regardless of which game is loaded).
- Responsibilities:
  - Injects its own `<style>` + a small fixed-position corner button (top-left), styled with the launcher's existing color tokens (`--highlight: #66fcf1`, dark translucent background) for visual continuity. Idle opacity ~0.35, full opacity on hover/focus/gamepad-hint, so it doesn't obscure gameplay.
  - Click → `window.location.href = '/'`.
  - Independent gamepad polling loop (its own `requestAnimationFrame`, reading `navigator.getGamepads()` directly) watching for **Select+Start held together** (buttons 8+9) for ~1.2s, with a small radial fill on the button while held, to avoid accidental triggers during normal play and avoid clashing with each engine's own input handling (RSDKv4's translator, SDL2 in Sonic3/Celeste).
  - No keyboard shortcut (e.g. Escape) claimed for this — needs verifying per-engine first (see Open Questions).

**2. Injection per game (reusing each build script's existing patch step)**

- **Sonic 1/2**: since we own `scripts/sonic/index.html` directly, add `<script src="/shared/launcher-overlay.js" defer></script>` before `</body>` in that file — no new tooling needed.
- **Sonic 3**: extend the existing Python patch block in `scripts/sonic3/build-sonic3-web.sh` (right after the ROM-helper patch) to also insert the same script tag before `</body>` in the deployed `index.html`.
- **Celeste**: extend `scripts/celeste/patch-gamepad-proxy.mjs` (or add one line to `build-celeste.sh` after it runs) to insert the same script tag before `</body>` in `public/game/celeste/index.html`.
- Because the script lives at a fixed `/shared/` path (not copied per-game), all three patch points just need one identical `<script>` tag inserted — no per-game content to keep in sync.

### Open Questions / Risks (need to verify during implementation, before considering this done)

1. **Does Escape already do something in-game?** RSDKv4 (Sonic 1/2) and Sonic3/Celeste may bind Escape to their own pause/menu screens. Plan is to *not* claim Escape and rely on the visible button + gamepad long-press, but this should be explicitly confirmed rather than assumed, in case a keyboard shortcut is still wanted for convenience.
2. **Immediate navigation vs. confirmation dialog:** Sonic 1/2/3 don't appear to have meaningful persistent in-run state beyond what's already flushed continuously (RSDKv4/S3AIR don't autosave mid-level to a degree that'd be lost). Celeste does have save data, but it persists to OPFS continuously via its own engine, independent of page navigation. Current plan is to navigate immediately with no confirm dialog — flagging in case this feels too easy to hit by accident.
3. **Z-index/stacking:** all three engines run a fullscreen canvas; need to confirm the overlay renders above it and doesn't get covered, and that `pointer-events` are scoped so the invisible padding around the button doesn't block clicks/touches meant for the game.

### 2026-07-05 - Extension: Replace RSDKv4's native Dev Menu with a web overlay (Sonic 1 first)

This directly resolves Open Question #1 above: confirmed in the vendored source (`.tmp/sonic1-wasm-build/RSDKv4/`) that `Engine.devMenu` is controlled by `DevMenu=true`/`false` in `settings.ini`, and **our shipped `scripts/sonic/settings-sonic-1.ini` / `-2.ini` already set `DevMenu=true`** — so Escape is currently bound today, opening RSDKv4's own native, in-canvas Dev Menu (`RetroEngine.cpp:126-148`, `ENGINE_INITDEVMENU` → `Debug.cpp:initDevMenu()`). Separately, F1 (reload stage), F2/F3 (prev/next stage), F10 (palette overlay), F12 (pause) and Backspace (fast-forward) are independent raw hotkeys, also gated by `Engine.devMenu`, but they act directly on engine state without opening any menu screen.

**User decisions (confirmed):**
- Scope: **only Escape** is replaced by the web overlay. F1/F2/F3/F10/F12/Backspace keep working exactly as they do today (native, untouched) — `DevMenu=true` stays as-is in `settings.ini` since those hotkeys depend on it.
- Visibility: the new web menu stays **accessible to anyone** (no `?dev=1` gating), matching today's behavior where Escape is already reachable by any player.
- Start with **Sonic 1** only; Sonic 2 follows afterward once verified (shared shell/build script, should mostly be "run it again").

**Why this is tractable:** the stage list is plain, inspectable data — `RSDKv4/Scene.hpp` declares `extern SceneInfo stageList[STAGELIST_MAX][0x100]` (each with a `name`/`folder`/`id`), `stageListCount[STAGELIST_MAX]`, and `stageListNames[STAGELIST_MAX]` (categories: Presentation, Regular, Bonus, Special). The existing F2/F3 handler (`RetroEngine.cpp:187-226`) shows exactly what "load stage N" requires: set `activeStageList`, `stageListPosition`, `stageMode = STAGEMODE_LOAD`, `Engine.gameMode = ENGINE_MAINGAME`, and reset the `lampPostID`/`starPostID` globals. Also confirmed the build already compiles with `--bind` (Emscripten embind) in the `wasm:` Makefile target — so bridging is a matter of adding embind-exposed functions, not raw `ccall`/manual string marshaling.

**Proposed technical plan:**

1. **New source file `RSDKv4/WebDevMenu.cpp`**, dropped into the build the same way `build-sonic-docker.sh` already patches `main.cpp`/`Audio.cpp`/`Input.cpp` (heredoc + sed-insert into the Makefile's `SOURCES` list). Exposes two embind-bound functions:
   - `std::string web_devmenu_get_stage_list()` — serializes `stageListNames`/`stageList`/`stageListCount` into a small JSON string (categories → stage names).
   - `void web_devmenu_load_stage(int listIdx, int stageIdx)` — mirrors the F2/F3 handler body above, so selecting a stage in the web menu behaves identically to using the native hotkeys.
   - Bound via `EMSCRIPTEN_BINDINGS(web_devmenu) { function(...); function(...); }`, callable directly as `Module.web_devmenu_get_stage_list()` / `Module.web_devmenu_load_stage(list, idx)` from JS (embind marshals `std::string`/`int` automatically — no manual `ccall`/buffer handling needed).
2. **`scripts/sonic/index.html`** (shared shell, edited directly):
   - Add a **capture-phase** `keydown` listener on `window` for `Escape` that calls `preventDefault()` + `stopImmediatePropagation()`, so the event never reaches the engine's own SDL handler (which would otherwise still open the native menu) — same "intercept before the engine sees it" idea as the existing gamepad→keyboard translator already in this file, just for a real (not synthetic) key.
   - New `#dev-menu-overlay` panel, styled consistent with the launcher (`--highlight` etc.): lists categories/stage names fetched once via `Module.web_devmenu_get_stage_list()` (after `onRuntimeInitialized`), navigable with Arrow keys / gamepad d-pad, Enter/A to call `Module.web_devmenu_load_stage(listIdx, stageIdx)` and close, Escape again to close without changing stage.
   - While the overlay is open, gate the existing gamepad-poll/key-passthrough so Sonic doesn't keep moving in the background behind the menu.
3. **Verification (Sonic 1 only for this pass):** rebuild via the existing Docker pipeline, confirm Escape opens the *new* HTML overlay (not the native text menu), the stage list matches real Sonic 1 stages, selecting one actually loads it, and that F1-F12/Backspace are unaffected. Also confirm the normal in-game Pause menu (Start button, `PauseMenu.cpp`, unrelated to Escape) still works untouched.
4. Only after Sonic 1 is verified, port the same three changes to Sonic 2.

### 2026-07-05 - Implementation: launcher-return overlay + fullscreen toggle + Sonic 1 dev menu

User approved and additionally asked for a Cmd+Enter (macOS) / Alt+Enter (Windows/Linux) shortcut to toggle native browser fullscreen. Decided (user choice) to add it to the shared cross-game script rather than Sonic-only, since it's a browser-level feature with no engine dependency.

**Implemented:**
- **`public/shared/launcher-overlay.js`** [NEW] — served at `/shared/launcher-overlay.js` (Astro serves `public/` at the site root, reachable from any `public/game/{slug}/` page). Contains:
  - A small corner button (top-left, 🏠, idle opacity 0.35 → 1 on hover/focus/hold) that navigates to `/` on click.
  - Gamepad long-press: holding Select+Start (buttons 8+9) together for ~1.2s also navigates to `/`, with a conic-gradient progress ring around the button while held.
  - Fullscreen toggle: `(metaKey || altKey) + Enter` calls `document.documentElement.requestFullscreen()` / `document.exitFullscreen()`.
  - Only wired into `scripts/sonic/index.html` for now (Sonic 1/2, via `<script src="/shared/launcher-overlay.js" defer>`). Sonic 3 and Celeste injection (via their existing post-build HTML patch scripts) remains follow-up work, per the original plan's step 2.
- **`RSDKv4/WebDevMenu.cpp`** [NEW, generated by `scripts/sonic/build-sonic-docker.sh`] — exposes `web_devmenu_get_stage_list()` (returns JSON: categories → stage names, read from `stageListNames`/`stageList`/`stageListCount`) and `web_devmenu_load_stage(listIdx, stageIdx)` (mirrors the native F2/F3 hotkey handler: sets `activeStageList`, `stageListPosition`, `stageMode`, `Engine.gameMode`, resets `lampPostID`/`starPostID`), both bound via Emscripten embind (`EMSCRIPTEN_BINDINGS`), callable directly as `Module.web_devmenu_get_stage_list()` / `Module.web_devmenu_load_stage(...)` — no `ccall`/manual marshaling needed since the build already used `--bind`.
- **`scripts/sonic/build-sonic-docker.sh`** — writes `WebDevMenu.cpp` via heredoc (same pattern as the existing `main.cpp` patch) and registers it in the Makefile's `SOURCES` list via a small Python string-patch (same style as Sonic 3's HTML patcher).
- **`scripts/sonic/index.html`** — new `#dev-menu-overlay` UI (styled with the launcher's color tokens) plus JS that: intercepts `Escape` in the capture phase (`preventDefault` + `stopImmediatePropagation`) so the native `ENGINE_INITDEVMENU` never triggers; on open, fetches/caches the stage list via embind and renders it as a flat, navigable list (Arrow keys, Enter, click, or gamepad D-pad/A/B — the existing gameplay gamepad→keyboard translator is gated off via `window.isDevMenuOpen()` while the menu is open so Sonic doesn't keep moving in the background); confirming a stage calls `web_devmenu_load_stage` and closes the menu; a second `Escape` closes without loading anything. F1/F2/F3/F10/F12/Backspace were left completely untouched (still native, still gated by `DevMenu=true` in `settings-sonic-1.ini`/`-2.ini`, unchanged).

**Verified (Sonic 1 only, per plan):** ran `scripts/sonic/build-sonic-docker.sh 1` (compiled cleanly, confirmed `WebDevMenu.cpp` included in the em++ invocation), then started the Astro dev server and drove headless Chromium via Playwright against `/game/sonic-1/index.html`:
- `Escape` opens the new HTML overlay (not the native text menu) — confirmed via DOM state, not just visually.
- Stage list renders 34 real entries across the correct categories (Presentation Stages: Title Screen, Ending 1, Staff Credits, Unlock All Achievements, Continue Screen, Level Select; Regular Stages: Green Hill Zone 1-3, Marble Zone 1-3, Spring Yard Zone 1-3, Labyrinth Zone 1-2, ...).
- Arrow-key navigation moves the selection correctly; `Enter` calls into the WASM module and actually loads the selected stage (console logs showed the engine loading that stage's data files, e.g. `Data/Stages/Ending/*`), then closes the overlay.
- Re-opening with `Escape` and closing with a second `Escape` leaves the game state untouched (no stage load).
- The `#launcher-return-btn` from the shared script is present on top of the game and clicking it navigates to `/`.
- `F3` (native hotkey) does **not** open the web overlay and doesn't error — confirms F-keys remain untouched/native as scoped.
- No `pageerror` entries in the browser console throughout.

Screenshots confirm the Dev Menu overlay renders correctly, styled consistently with the launcher (dark background, `--highlight` cyan), and the return-to-launcher button renders in the top-left corner over the title screen.
