## 2026-07-05 20:02: Decoupled Logic from Rendering for Sonic 1, 2, and Mania

Following the successful decoupled engine patch for Sonic CD (RSDKv3), we expanded this architecture to all other games in the collection.

### Overview of Changes
In the original native loop architecture (across RSDKv4 and RSDKv5), the game logic (`ProcessEvents`, `ProcessNativeObjects`, `CheckFPSCap`) was strictly tied 1:1 with drawing a frame (`FlipScreen`). On WebAssembly (`requestAnimationFrame`), this caused:
1. Slowdown to 50% speed on 30Hz display modes (e.g. macOS Low Power Mode / Battery mode).
2. Wasted compute power processing redundant game ticks on 120Hz / 144Hz displays.

We implemented an **Accumulator-based while loop** that separates physics ticks from visual rendering:
- **Sonic 1 & 2 (RSDKv4)**: Added a Python patching block to `build-sonic-docker.sh`. It intercepts `RetroEngine::Run()`, replaces the `SDL_Delay` logic with a software accumulator `while (curTicks >= targetFreq)`, runs the logic loop up to 4 times per browser tick to catch up on dropped frames, and calls `FlipScreen()` once at the end.
- **Sonic Mania (RSDKv5U)**: Modified the existing Python patch in `build-sonic-mania-docker.sh` that overrides `RunRetroEngineFrame()`. Instead of returning early if `CheckFPSCap()` is false, we maintain our own `emsCurTicks` accumulator and run a `while` loop that calls the game logic. `FlipScreen()` remains at the end to commit the frame to the WebGL canvas.

- `make build.sonic-mania` (Sonic Mania) compiled successfully.

All games will now flawlessly retain 60 logic ticks per second regardless of the monitor's native refresh rate or power-saving modes.
