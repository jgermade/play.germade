# Engine Subprojects Split (independent repos + WASM SDK contract)

- **Date:** 2026-07-09 21:44
- **Status:** In Progress

## Goal

Split each emulator/game engine into its own independent repository. Each engine
repo builds its own `.wasm` in CI and exposes a **JS SDK** to interact with it.
The app (`play.germade`) becomes a pure consumer. All engines conform to **one
shared contract** so the app drives every engine through an identical interface.

## Decisions (confirmed with user)

1. **One engine = one folder = one repo.** Engines live under `engines/<engine>/`
   locally, but each is `git init`'d as its **own** repository. The parent
   `play.germade` repo **git-ignores** `engines/` entirely (no submodules).
2. **WASM is built in CI**, not committed. Each engine repo's CI **attaches the
   built `.wasm` to a GitHub Release**.
3. **App fetches the `.wasm` at *build time*** (a build-step syncs the pinned
   release asset into the app), giving version pinning + small repo + no runtime
   CDN dependency.
4. **Shared contract lives in a dedicated repo:** `github.com/wasm-gaming/wasm-specs`.
   Every engine repo and the app conform to it — single source of truth.

## Key finding: Sonic 1 & 2 share one engine `.wasm`

Verified against `scripts/engines/rsdkv4/build-rsdkv4-docker.sh`:
- The `[1|2]` build arg only selects **paths** (asset dir, settings file, output
  dir). There is **no per-game compile define** — the RSDKv4 C source compiled is
  identical for both games.
- Per-game data enters only via Emscripten `--preload-file Data.rsdk
  --preload-file settings.ini`, which lands in a separate `.data` package + JS
  loader, **not** in the `.wasm`.
- **Conclusion:** one `rsdkv4` engine + `.wasm` serves both games; `Data.rsdk` +
  `settings.ini` become **runtime-loaded assets**, not compile-time bakes.
- Same collapse applies to RSDKv3 (Sonic CD) and RSDKv5U (Sonic Mania) as
  reusable cores. RSDKv4 and SMW are the only current "bake at compile time"
  outliers to convert to runtime-load.

## The contract (`wasm-gaming/wasm-specs`)

Two layers. Differences between engines (Data.rsdk vs ROM zip+BIOS vs baked
assets vs .NET/OPFS) become **data in a manifest**, not different APIs.

### Layer A — declarative `EngineManifest`

```ts
interface EngineManifest {
  id: string;                    // "rsdkv4" | "fbneo" | "blastem" | "jgenesis" | "smw"
  version: string;
  artifacts: { wasm: string; js: string; data?: string };  // wasm = release asset URL/ref
  assets: AssetSpec[];           // files supplied at runtime
  input: string | KeyMap;        // reuse existing 'rsdkv4' | 'rsdkv5' presets
  video: { baseWidth: number; baseHeight: number; aspect?: string };
  options?: JSONSchema;          // engine-specific settings (e.g. SMW ExtendedAspectRatio)
  capabilities: { saveStates?: boolean; sram?: boolean; coreSelectable?: boolean };
}

interface AssetSpec {
  key: string;                   // "data" | "rom" | "bios"
  mountPath: string;             // "/Data.rsdk", "/roms/neogeo.zip"
  required: boolean;
  accept?: string[];             // [".rsdk"] / [".bin"] / [".zip"]
  validate?: { bytes?: number; sha1?: string };   // e.g. Sonic3 ROM must be 4,194,304 bytes
}
```

### Layer B — imperative runtime interface (every engine SDK implements this)

```ts
export interface EngineSDK {
  manifest: EngineManifest;
  load(config: EngineConfig): Promise<EngineInstance>;
}

interface EngineConfig {
  canvas: HTMLCanvasElement;
  assets: Record<string, Uint8Array | Blob>;   // keyed by AssetSpec.key
  options?: Record<string, unknown>;
  persist?: 'idbfs' | 'opfs' | null;
  onEvent?: (e: EngineEvent) => void;
}

interface EngineInstance {
  start(): void; pause(): void; resume(): void; reset(): void;
  setInput(map: KeyMap): void;
  saveState?(): Promise<Uint8Array>;            // capability-gated
  loadState?(data: Uint8Array): Promise<void>;
  screenshot?(): Promise<Blob>;
  destroy(): void;
}

type EngineEvent =
  | { type: 'ready' } | { type: 'error'; error: Error }
  | { type: 'exit' }  | { type: 'frame'; fps: number };
```

### Why it fits the existing engines
- `Data.rsdk` / `rom.bin` / `neogeo.zip`+BIOS → all just `AssetSpec` entries with
  different `mountPath`/`validate`. BlastEm's `FS_createDataFile` quirk and
  Sonic3's IDBFS ROM injection hide behind `load()`'s asset-mount step.
- `#canvas` id requirement, AudioContext resume, and the gamepad→keyboard proxy
  (today's `public/shared/game-input.js`) become the SDK's responsibility.
- SMW (baked, `RM_MINE`) = manifest with empty `assets[]` + optional bundled
  `.data`; same interface, no ROM picker shown.
- Megadrive core choice (JGenesis vs BlastEm) = two manifests with the same
  `rom` `AssetSpec`; launcher swaps SDKs, contract unchanged.
- Caveat: `saveState`/`screenshot` aren't implementable on every core — hence
  optional + `capabilities`-gated.

## Proposed layout

- `github.com/wasm-gaming/wasm-specs` — contract repo (TS types + manifest schema
  + conformance typecheck). Consumed by every engine repo and the app.
- `github.com/wasm-gaming/<engine>` — one per engine (rsdkv3/v4/v5, fbneo,
  blastem, jgenesis, smw, celeste, sonic3air). CI builds `.wasm`, attaches to a
  Release, publishes/exposes the JS SDK conforming to the contract.
- `play.germade` (this repo):
  - `.gitignore`: add `engines/` (whole tree ignored).
  - Keep an un-ignored `engines.json` (or `scripts/bootstrap-engines.sh`) listing
    engine repo URLs + pinned release versions, so a fresh clone can be
    reconstructed and the build-time WASM fetch knows what to pull.
  - Build-time step: fetch each pinned engine Release `.wasm` into `public/` (or
    an ignored cache) + wire manifests into the launcher.

## Open questions / TODO before implementation

2. Whether engine SDKs are published to npm or vendored from release assets too.
3. `wasm-specs` distribution: git dependency vs published npm package.
4. Migration order for the remaining engines after the reference is validated.

   `manifest.json`) + `DEFAULT_RSDKV4_OPTIONS`. The SDK now **generates
   `settings.ini` from `config.options`** (devMenu / engineDebugMode / vsync /

3. **Renamed** `src/sdk.js` → `src/rsdkv4.sdk.js`; updated `package.json`
   (`main`/`exports`, added `./options` export) and `example/index.html` (import
   path + a minimal launcher-owned Escape→pause+getStageList demo).

**FS clarification (answered, no code change needed):** `Module.FS` here is the
**legacy JS FS API backed by MEMFS** — in-memory, *not* WASMFS and *not* OPFS.
The build uses `-sFORCE_FILESYSTEM=1` but not `-sWASMFS`, so
`FS.writeFile('/Data.rsdk')` writes to MEMFS (transient, correct for boot data /
a `--preload-file` replacement). OPFS is only reachable via `-sWASMFS`. RSDKv4
has `sram:false`, so no persistence is needed; if that changes, use IDBFS
(legacy + `FS.syncfs`) or OPFS-under-WASMFS, and re-verify `FS` call timing.

## Extension — 2026-07-09 23:55 — rsdkv4 → TypeScript build + dist pipeline + WASMFS/OPFS

User direction: split the demo out, generate a real `dist/` (with `.d.ts`), and
move the filesystem off MEMFS to WASMFS/OPFS.

**Premise corrected:** MEMFS is not formally deprecated, but WASMFS is
Emscripten's modern/eventual-default FS. Key asymmetry driving the design:
`-sWASMFS` alone = an in-memory WASMFS backend (a safe MEMFS replacement, still
single-threaded, no new host requirements); **OPFS** additionally needs
worker/`-pthread` proxying + **COOP/COEP** cross-origin isolation, which is risky
against this SDL2 + `emscripten_set_main_loop` build and can't be validated here.

Implemented (all in the rsdkv4 repo):
- **SDK is now TypeScript.** `src/rsdkv4.sdk.ts` (was `.js`). Imports the typed
  manifest + options directly, so the earlier JS/TS default-options drift is gone.
- **Typed manifest** `src/rsdkv4.manifest.ts` — `EngineManifest` typed against the
  contract (compile-time conformance ✓, closes the earlier follow-up).
  `build:manifest` serializes it to `dist/manifest.json`. Removed root
  `manifest.json`.
- **Demo split** `example/` → `src/demo/{index.html,demo.ts}`. `demo.ts` →
  `dist/demo.js`, consumes the SDK **by package name** via an import map in
  `index.html`; auto-loads a git-ignored `dist/Data.rsdk`, picker fallback.
- **Two tsconfigs**: `tsconfig.json` (lib → flat `dist/`), `tsconfig.demo.json`
  (demo → flat `dist/`, resolves the SDK from built `.d.ts`). `paths` maps
  `@wasm-gaming/wasm-specs` → `../wasm-specs/dist/index.d.ts` (type-only, erased).
- **Filesystem WASMFS/OPFS:** `build.sh` links `-sWASMFS` and adds `WebFS.cpp`
  (`web_mount_opfs` → OPFS backend). SDK `mountWorkingDir()` mounts OPFS at `/data`
  when `crossOriginIsolated`, else in-memory WASMFS; writes `Data.rsdk` +
  generated `settings.ini` to `/data`; `FS.chdir('/data')` + `callMain(['UsingCWD'])`
  so the engine reads from the (persistent) CWD. Asset `mountPath`s updated to
  `/data/*`.
- `package.json` build pipeline (`build`, `build:lib/manifest/demo/web`,
  `typecheck`, `serve`) + `exports` (`.`, `./options`, `./manifest`) pointing at
  `dist/`, `typescript` devDep. CI now builds TS + WASM and attaches the full dist
  (fetches the sibling contract repo first).

**dist/ layout produced (verified locally):** `rsdkv4.sdk.{js,d.ts}`,
`rsdkv4.options.{js,d.ts}`, `rsdkv4.manifest.{js,d.ts}`, `manifest.json`,
`demo.js`, `index.html` (+ `.map`s). WASM stage adds `rsdkv4.{js,wasm}`.
`dist/Data.rsdk` assumed git-ignored (covered by `dist/` + `*.rsdk`).

**Verified:** full TS build compiles clean (strict); dist layout matches the
requested files; `dist/manifest.json` validates against the contract; `demo.js`
preserves the bare `@wasm-gaming/engine-rsdkv4` specifier for the import map.

**NOT verified (open):** the Emscripten WASM build (`build:web`) — so `-sWASMFS`,
the `WebFS`/OPFS helper, `UsingCWD`+`/data` read path, and the whole runtime-load
are unproven. **OPFS specifically** likely needs `-pthread` + COOP/COEP and a real
build to work at all; today it's gated + falls back to in-memory WASMFS. Next:
run `build:web` (Docker) + the demo with a real `Data.rsdk`; decide whether to
commit to the pthread/COOP-COEP path for true OPFS persistence.
