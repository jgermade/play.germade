# Mobile: a grid of games, details below the one you tap

_2026-11-14_

## Context

Owner, with a phone screenshot of the launcher: "En mobile, pondría el grid de juegos, y al hacer
click en cada uno, que aparezcan sus detalles y acciones debajo". Today, under 760px, the page is the
desktop TV layout squeezed: a tall hero (title, chips, description, Instalar) that takes most of
the screen, the rows scrolling sideways with tiles cut at the edge, and the keyboard/pad hint bar
overlapping the tiles.

## Plan (≤ 760px only; desktop/TV unchanged)

1. **No hero.** The `Hero` is hidden; the page is the top bar and the rows.
2. **Rows become grids.** Each row's `.cards` wraps into a grid (3 columns; 2 below ~360px)
   instead of a sideways strip, so every game is visible without horizontal scrolling. Captions
   keep title + year.
3. **Tap a game → its details open below it**, like the emulators' iOS-6 folder already does: a
   full-width panel inserted after the grid line that holds the tile, with the notch pointing at
   it. The panel is the hero's content — kicker, title, chips (year, engine, Instalado /
   Próximamente), description and the actions (Jugar / Instalar / Quitar datos). Tapping the same
   tile again, or another one, closes / moves it. The first tap no longer launches the game; the
   panel's button does.
4. **Emulators** keep their ROM folder on tap (it already opens below the tile); the folder gets
   the same "grid line" placement.
5. **Hint bar** hidden on touch screens (`pointer: coarse`): it lists keyboard/pad keys and covers
   the last tiles.
6. Keyboard/pad on desktop keep today's behaviour (Enter opens directly).

Implementation notes: the panel is a `<li>` with `grid-column: 1 / -1` rendered inside `.cards`
after the last tile of the tapped tile's line (columns read from the grid's computed
`grid-template-columns`); the hero's markup is reused through a shared component
(`GameDetails.html`) so both stay in sync. `matchMedia('(max-width: 760px)')` decides whether a tap
opens details or launches.

**Verify:** `npm test`; build + preview screenshots at 390×844 (grid; details open on a game, on an
installed game, on a "Próximamente" one; ROM folder on an emulator) and at 1440×900 (unchanged).

## 2026-11-14 — Extension: the page scrolls on mobile (pull to refresh)

Owner: "En mobile, ¿por qué no se usa el scroll de la página? No puedo tirar hacia abajo para
actualizar". Cause: the TV frame — `html, body { height: 100%; overflow: hidden }` and a
`.launcher` exactly `100dvh` tall, with `.rows` as its own scroll container. The document never
scrolls, so the browser's pull-to-refresh (which needs the page at its top, scrolled by the
document) never starts.

Change (≤ 760px only): `html, body` back to `height: auto` and `body` scrolling; `.launcher`
`height: auto; min-height: 100dvh`; `.rows` without its own overflow. The console sheet keeps its
own scroller (`overscroll-behavior: contain`), and the page behind it does not scroll while it is
open (`body.has-sheet { overflow: hidden }`). Desktop/TV keep the frame.

### Walkthrough of the extension

- `src/styles.css` (≤ 760px): `html, body { height: auto }`, `body { overflow: visible }`,
  `body.has-sheet { overflow: hidden }`, `.launcher { height: auto; min-height: 100dvh }`,
  `.rows { overflow: visible }`.
- `src/App.html`: `body.has-sheet` toggled with the console sheet; the details panel is scrolled
  into view 260ms after opening (once rendered and unfolded — before, it could stay half off
  screen).

**Verified** (iPhone 13 emulation): the document scrolls (scrollY 0 → 192 on a wheel), `.rows` has
no scroller of its own; the Mania panel, which ended at 759px on a 683px screen, is now scrolled
fully into view; with a console open the body is locked and unlocked on back; desktop keeps the
frame (body `overflow: hidden`). `npm test` 22/22, no page errors. Pull-to-refresh itself is the
browser's and cannot be driven from Playwright; it needs the owner's phone.

Commit: `fix(mobile): the page scrolls, so pull-to-refresh works; details scroll fully into view`

## 2026-11-14 — Proposal: the page scroll on desktop too, with scroll snap (awaiting approval)

Owner: "Intentaría también usar el scroll de la página en desktop, ¿no se podría hacer que
funcione parecido a como está ahora con scroll snap?"

Today (desktop/TV): a frame of `100dvh` — top bar and hero fixed, `.rows` scrolls inside the rest;
moving the focus scrolls the active row to the top of `.rows` (JS), and a CSS mask fades the rows
at the top edge.

Proposal:
1. The document scrolls on every size (one model for phone and desktop); `.rows` loses its own
   scroller.
2. Top bar + hero become a **sticky header** (`position: sticky; top: 0`), so the hero keeps
   showing the focused item while the rows move under it.
3. **Scroll snap on the page**: `html { scroll-snap-type: y proximity; scroll-padding-top:
   <header height> }` and `.row { scroll-snap-align: start }` — wheel/trackpad scrolling settles
   with a row right under the hero, like today. `proximity`, not `mandatory`: a long open ROM folder
   must stay freely scrollable.
4. Keyboard/pad: moving the focus scrolls the window to the active row (`scrollIntoView` honours
   the scroll padding) instead of scrolling `.rows`.
5. **What hides the rows that go under the header**: the header has no solid background (the
   backdrop is the blurred art), so rows passing under it would show through the title. Today the
   frame's mask hides them. Proposed: rows whose top is above the header's bottom fade out
   (`IntersectionObserver` with the header height as negative root margin → `.row.is-under`
   with `opacity: 0`), which looks like today's fade.
6. The bottom padding that lets the last row reach the top stays.
7. Scrolling with the wheel moves the focus to the row that snaps under the hero (so hero and
   rows agree), first tile of that row unless it already had the focus.

Mobile keeps what #15 does (no hero, plain page).

**Verify:** 1440×900 and 1100×760: wheel → rows snap under the hero; arrows still move row by row;
an open ROM folder scrolls freely; rows under the header are hidden; phone unchanged.
