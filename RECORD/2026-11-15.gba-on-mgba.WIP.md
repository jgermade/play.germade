# Game Boy Advance (and Game Boy / Color) on mGBA — 2026-11-15

Status: **proposal, awaiting approval.** Depends on mGBA-wasm's contract 1.0 + engine app
(`RECORD/2026-11-15.contract-1.0-states-and-engine-app.WIP.md` there).

## Plan

1. **`src/data/systems/gba.js`** — pure identification, as `snes.js`:
   - GBA: `.gba` (+ `.agb`); header title at 0xA0 (12 bytes), game code at 0xAC (4, the serial),
     version at 0xBC; header checksum at 0xBD validates.
   - Game Boy / Color: `.gb` / `.gbc` (+ `.sgb`); title at 0x134 (11–16 bytes), CGB flag 0x143,
     version 0x14C, header checksum 0x14D. Same entry, the system field says which.
   - DAT match (ROM Manager's dataset) still comes first.
2. **Registry + catalog** — the existing `gba` entry (already "GBA, Game Boy Color y Game Boy con
   mGBA") gets the systems; the touch pad uses engine-specs' `gba` / `gb` layouts by ROM.
3. **engines.json** — `mgba` pinned to the mGBA-wasm release with the app (`app/app.js`); entry
   flips to `status: 'ready'` once that release exists, as with snes9x.
4. **Tests** — `tests/gba.test.mjs` with synthetic headers (GBA, GB, GBC).

## Extension (2026-11-15 17:46 UTC) — who recognizes the ROMs

ROM Manager already recognizes all three: `.gb` / `.gbc` / `.gba` go to its `GAMEBOY` /
`GBC` / `GBA` systems and are identified by CRC32 against its No-Intro datasets (with
libretro-thumbnails boxarts). Nothing to change there.

play.germade reuses those datasets (`src/data/datasets.json`, pinned to rom-manager
`d23406e`) but lists only `GBA` today. So the plan grows by one step, and the header reader of
step 1 becomes the fallback only (hacks, homebrew, dumps missing from the DAT):

0. **datasets.json** — add `gb: "GAMEBOY"` and `gbc: "GBC"` (same pinned commit), so all three
   are matched by checksum first, with boxart, exactly as in ROM Manager.
