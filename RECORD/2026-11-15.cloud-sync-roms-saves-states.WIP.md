## Scope: the origin, not a page

Every route — `/`, `/sonic1/`, `/megadrive/`, `/neogeo/`, `/roms/` … — is a page of the same origin
over **one OPFS** (`2026-11-13.routes-engine-menus-and-shared-opfs.WIP.md`). So the sync is **one
service for the whole origin**: whatever page wrote a file, it is synced; whatever page is open
shows the same sync state. It is not a feature of one route.

What it covers, on today's layout:

```
library/<system>/roms/<sha1>.<ext>    ROMs — content-addressed, so the same ROM is the same path everywhere
library/<system>/patches/<sha1>.*     ROM-hacking patches
library/<system>/index.json           games → versions, chosen core, mods (the user's choices)
<engine>/<namespace>/…                save games (SRAM), save states (slot_N.*, slot_N.png, slot_N.lock),
                                      and, for the ports, the installed data packs
```

Not covered: the engines (served, cached by the service worker), cover art (service worker
cache), and each node's `.vfs/` control folder (its own, by design).

## Findings that shape the design

1. **Drive works from the browser; Box does not, today.** Drive: Google Identity Services token
   client, a public client id, CORS-enabled REST API, and `@cloudauthn/vfs-sync` (the owner's
   library) already ships `GDriveAdapter` and `OPFSAdapter`. Box: the code is exchanged "along
   with its client secret" ([Box OAuth 2.0](https://developer.box.com/guides/authentication/oauth2)),
   no PKCE; downloads redirect to `dl.boxcloud.com`, which "does not support Cross Origin Resource
   Sharing" ([in-browser downloads](https://developer.box.com/guides/downloads/in-browser));
   chunked uploads only from 20 MB ([chunked uploads](https://developer.box.com/guides/uploads/chunked)).
2. **The launcher is cross-origin isolated, and Google's sign-in popup is not compatible with
   that.** `src/sw.js` adds `Cross-Origin-Opener-Policy: same-origin` and
   `Cross-Origin-Embedder-Policy: require-corp` to every navigation (the engines need
   `SharedArrayBuffer`). `same-origin` cuts the link between the page and the Google popup, and
   `require-corp` blocks the GIS script itself. Google documents `same-origin-allow-popups` for its
   popup — which is not isolation. To be confirmed in the browser, but it decides where sign-in
   happens (Phase 1).
3. **Every route is a new document** (Vite MPA), so a token kept in memory is lost on every
   navigation — home → `/megadrive/` would ask Google again.
4. **A gamepad press is not a user activation.** Browsers open a popup only after a tap, a click
   or a key. Connecting, and renewing the 1-hour token, needs one of those; syncing with a valid
   token does not.
5. **A running emulator holds its saves in memory.** BlastEm copies `blastem/<ns>/` into MEMFS at
   start and writes changed files back on flush (`#restoreSaves` / `#flush`). A save pulled into
   OPFS while it runs would be overwritten by the next flush, or would overwrite it.
6. **`GDriveAdapter` uploads whole files** (`uploadType=media`, one `Uint8Array`): a 100 MB Neo Geo
   set or a data pack sits whole in memory, and a dropped connection starts over.
7. **`drive.file`** gives access only to files the app created: the app's own folder works; files a
   user drops into it through drive.google.com stay invisible. Full `drive` is a restricted scope
   (Google security assessment).

## Design

### Nodes: one per top-level folder

One `VFSNode` per `library/<system>/` and per `<engine>/`, over `OPFSAdapter.open({ path })`,
each paired with the same path under the Drive folder `play.germade/` (a `ScopedAdapter` over one
`GDriveAdapter`). Per folder, because:

- **Each device chooses which systems' ROMs it keeps** — a phone can skip Neo Geo sets and still
  get every save. Saves and states (`<engine>/`) always sync.
- **A running game blocks only its engine's folder**; the rest keeps syncing.
- A failure in one folder does not stop the others.

### Coordination between routes and tabs

- **Web Locks**: `navigator.locks.request('cloud-sync', …)` — one sync at a time across every page
  and tab of the origin.
- **A game route holds `opfs:<engine>`** from before the engine starts until its saves are flushed
  on exit. The sync takes the same lock before touching that folder; when it is held, the folder
  is skipped this round and reported as "en uso". Finding 5 cannot happen.
- **`BroadcastChannel('cloud-sync')`**: state (connected, syncing, done, conflicts, needs a tap)
  reaches every open page, so any route shows the same status.

### Sign-in

- **On a page that is not isolated**: a `/cloud/` route that the service worker serves **without**
  COOP/COEP (finding 2). It loads GIS (only there, only on demand), opens the popup, and goes back.
  The sync itself — plain CORS `fetch` to `googleapis.com` — works from isolated pages, so every
  other route stays as it is.
- **Token in `sessionStorage`** with its expiry: same origin, this tab, survives navigation
  (finding 3), gone when the tab closes. Never `localStorage`. The risk accepted: script running on
  the origin could read a 1-hour token whose `drive.file` scope only reaches the app's own folder.
- **The link** (provider, Drive folder id, account hint, this device's systems) in IndexedDB — not
  secret.
- When the token expires, syncing pauses and every page says "Toca para reconectar" (finding 4).
- "Desconectar" revokes the token and forgets the link; the local files stay.

### When it syncs

- **Linking a device**: the first sync shows its plan — what comes down, what goes up, how much —
  and runs only once approved.
- **Afterwards, automatically, while a token is valid**: on start (pull), before a game route
  starts its engine (pull that engine's folder), after a game route exits (push it), after ROMs are
  added (`/roms/`, the drawers: push that system). Approved without asking **when nothing is
  deleted and nothing conflicts**; otherwise the plan is shown (vfs-sync's `approveMerge`).
- **A "Sincronizar ahora" button** on the home and in settings.

### Conflicts

- **Saves and states are binary**: the newest wins and the other is kept beside it as a conflict
  copy (`slot_1 (conflict <peer> <id>).state`). The engines look slots up by exact name, so a copy
  never confuses them; the launcher lists pending conflicts per game ("este dispositivo / el otro")
  and settles them with `resolve()`.
- **The auto suspend point** (BlastEm's slot 9, "where you left off"): synced — leave on the PC,
  continue on the phone — and newest wins **without** a copy, or every switch of device would
  leave one. A per-path policy; checked against vfs-sync's conflict rules (`docs/conflicts.md`).
- **`index.json`**: a JSON-aware merge keyed by game and version (union of entries, newest choice
  per entry), plugged into vfs-sync's custom merge — a line-based three-way merge could produce
  invalid JSON.
- ROM files cannot conflict: same content, same name. Drive's `sha1Checksum` checks every
  download against its file name for free.

### Large files

Resumable uploads in `GDriveAdapter.writeStream()` (`uploadType=resumable`, 8 MiB chunks,
resume from the offset the session reports, backoff): memory stays flat and a dropped connection
continues. That is the owner's library (`cloudauthn/vfs-sync`), not attached to this session.

## Box

Spike before any code: a Box app with `https://play.germade.dev` and the dev origin allowlisted;
from a test page, `fetch` a file's content (does the redirect to `dl.boxcloud.com` pass CORS?), a
`Range` read, a direct and a chunked upload.

- If content and uploads work cross-origin, the only backend is a **token worker** (a Cloudflare
  Worker on, say, `auth.play.germade.dev`, ~100 lines): it holds the client secrets and keeps the
  refresh token in an encrypted `HttpOnly` cookie — no database, and no file ever passes through
  it. The same worker would also give **Drive** long sessions (Google refresh tokens), removing the
  hourly "Toca para reconectar" — worth it on a TV with a gamepad.
- If downloads need a proxy, every ROM and save would pass through a server of ours.
  Recommendation then: **no Box**.
- Only after that, a `BoxAdapter` in vfs-sync: ids from Box, `list` with
  `fields=name,size,modified_at,sha1`, `Range` reads, direct upload ≤ 50 MB and chunked above,
  `If-Match` on the etag for `writeIf`.

## Extension (2026-11-15 12:27) — one connection for the whole site, through a cookie

Owner: "Y si va por cookies, quizá también se pueda compartir la conexión con GDrive y Box, entre
el home y el rom manager".

`/roms/` is the same origin as the home and the game routes (`2026-11-13.rom-manager-and-mods.WIP.md`),
so whatever holds the connection is already shared by origin; the question is how long it lives
and whether every tab sees it. Through a cookie, it does, and it fixes more than that.

### How

The token worker of the Box section becomes the way to connect **both** providers:

1. "Conectar Google Drive / Box" **navigates** (no popup) to
   `https://auth.play.germade.dev/connect/<provider>`, which redirects to the provider's consent
   page.
2. The provider returns to the worker's callback; the worker exchanges the code (with the client
   secret, which never leaves it) and sets a cookie holding the **refresh token, encrypted**
   (AES-GCM, key in the worker's secrets): `HttpOnly`, `Secure`, `SameSite=Strict`, host-only on
   `auth.play.germade.dev`. Then it redirects back to the page that started.
3. Any page of play.germade.dev — home, `/roms/`, `/megadrive/`, any tab — asks
   `fetch('https://auth.play.germade.dev/token/<provider>', { credentials: 'include' })` and gets a
   fresh **access token** (1 h), kept in memory only. Both hosts are the same site (`germade.dev`),
   so a `SameSite=Strict` cookie is sent; the worker answers with
   `Access-Control-Allow-Origin: https://play.germade.dev` and `Allow-Credentials: true`, which a
   `require-corp` page accepts (it is a CORS response).
4. "Desconectar" calls the worker, which revokes the token at the provider and clears the cookie.

### What it fixes, against the findings

| finding | browser-only (Drive) | with the cookie |
| --- | --- | --- |
| 2 · COOP/COEP vs the Google popup | needs a non-isolated `/cloud/` page | no popup, no GIS script — a navigation |
| 3 · each route is a new document | token in `sessionStorage`, per tab | every page and tab asks the worker |
| 4 · a gamepad press is not a user activation | a tap every hour | a navigation needs no activation; renewing is a `fetch` — never a tap after connecting |
| connection lifetime | until the tab closes | until the refresh token is revoked or expires (Box: 60 days of disuse) |
| Box | impossible | possible (pending the CORS spike for content) |

What the worker never does: hold a file, see a file, keep a database. Its state is the cookie the
browser keeps. What it costs: a Cloudflare Worker on `auth.play.germade.dev` (free tier), the two
client secrets in its secrets, and one more thing to deploy.

Not shared: rom-manager served on its own (`wasm-gaming.github.io/rom-manager/`) is another site;
it would get its own connection, if ever.

### What changes in the plan

- The `/cloud/` route stays as the settings page (systems for this device, conflicts, "Sincronizar
  ahora", connect / disconnect), but it no longer needs to be served without COOP/COEP; `src/sw.js`
  is not touched.
- `sessionStorage` is not used; `src/services/cloud/auth.js` becomes a small client of the worker.
- New: the worker (its own repo or a folder here — the owner's choice), with tests for the code
  exchange, the cookie's encryption, revocation and CORS.
- Phase 1 becomes "the worker + Drive through it"; Box (phase 4) keeps its CORS spike, now without
  the auth question.
- If the owner prefers no backend at all, the browser-only variant above stays valid for Drive,
  with its limits (a tap every hour, per tab).

### Open decision 1, restated

**Token worker on `auth.play.germade.dev`** — recommended: one connection for the home, `/roms/`
and every route and tab, no hourly tap, Box possible — or **no backend**: Drive only, per tab.
